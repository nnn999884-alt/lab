# 급등주 데이터셋 · 자동 학습 · 실시간 신호 설계

작성일: 2026-10-28 · 상태: 승인 대기 · 관련: `2026-10-28-momentum-redesign-design.md`

## 1. 목표

1. **놓친 급등주까지 전부 데이터로 남긴다** — 잡았든 못 잡았든 그날 +30% 이상 간 종목을 모두 기록하고, 못 잡았다면 **왜** 못 잡았는지 분류한다.
2. **스스로 학습한다** — 주 1회, 잡은 것과 놓친 것의 특징 차이에서 조건 후보를 만들고, 과거 데이터로 검증해 통과한 것만 채택한다.
3. **신호를 실시간으로 받는다** — 웹소켓 체결 기반으로 1~2초 내 감지, 2~3초 내 주문, 동시에 텔레그램 푸시.

## 2. 데이터셋

### 2.1 현재 상태 (실측)

| 데이터 | 현재 | 부족한 점 |
|---|---|---|
| `daily_bars` | 2025-01-02~2026-10-27, 197,743행 | 종목당 평균 92봉 (2년이면 ~460봉 필요) → **백필 필요** |
| 분봉/현재가/호가 | 10/22~10/28 (4~5일) | 과거 분봉 없음 |
| 공매도·대차 | 10/22~ (5일) | 과거 이력 없음 (소스가 당일 파일만 제공) |
| **`runners` (급등주)** | **0행** ← 기록 로직이 안 돌고 있다 (버그) | 즉시 수정 필요 |

### 2.2 새 테이블

| 테이블 | 키 | 내용 |
|---|---|---|
| `runner_events` | (trade_date, symbol) | prev_close, open/high/low/close, volume, dollar, change_pct, close_loc, rotation, gap_pct, first_alert_ts, source |
| `runner_features` | (trade_date, symbol) | 유통주식, 희석 점수/이벤트, 공매도 비율, 대차 수수료, SSR, 랭킹 최고순위, 데이마켓 등락, 프리마켓 등락, ATR 비율, 박스 상단 거리, 뉴스/공시 플래그 |
| `runner_outcomes` | (event_date, symbol, horizon) | `T+0_high`, `T+0_close`, `T+1_pre`, `T+1_open`, `T+1_close`, `T+3_close`, `T+5_close` (진입 가능 시각 기준 수익률) |
| `runner_misses` | (trade_date, symbol) | `miss_reason` (아래 분류), `detail`, `setup`, `first_seen_ts` |
| `candle_jobs` | (symbol, interval, cursor) | 백필 진행 상태 (재시작해도 이어서) |

### 2.3 미스 사유 분류

| 코드 | 뜻 | 판정 근거 |
|---|---|---|
| `not_in_universe` | 유니버스($0.2~$10)에 없었음 | `universe` 스냅샷 |
| `price_out_of_range` | 매매 가격범위($0.5~$5) 밖 | 현재가 |
| `spread_too_wide` | 스프레드 상한 초과 | quotes |
| `low_dollar_volume` | 거래대금 부족 | prices/rankings |
| `filter_reject:<rule>` | 셋업 필터 탈락 (예: 희석 60점 이상) | signals.reason |
| `risk_block` | 리스크 규칙 차단 (동시보유·손실한도) | signals.reason |
| `halted` | 거래정지 중 | halts |
| `already_held` | 이미 보유 | trades |
| `too_late` | 우리 기준으로 이미 +30% 초과 (추격 금지) | prices |
| `no_setup_matched` | 조건에 맞는 셋업 없음 | signals 부재 |

## 3. 자동 학습 루프

### 3.1 주기
- **매일** 마감 후: `runner_events` 기록, `T+0` 결과 채움, `runner_misses` 분류
- **매일**: T+1·T+3·T+5 결과가 나온 과거 이벤트의 `runner_outcomes` 갱신
- **주 1회**(일요일): 학습 → 후보 규칙 → 검증 → 채택/폐기 → 리포트

### 3.2 학습 방법 (해석 가능하게)
1. 특징별 **lift**: 잡은 러너 vs 놓친 러너의 중앙값 차이와 백분위 분포 비교
2. 후보 규칙 생성: "거래 회전 ≥ 0.45 & 유통주식 < 2천만 & 희석 < 70" 처럼 **사람이 읽을 수 있는 조건**으로
3. 후보를 과거 70%로 적합, 뒤 30%로 검증 → **검증 구간에서 기대값 양수 + 표본 20건 이상**일 때만 채택
4. 채택 결과: 셋업 점수 가중치, 임계값, 셋업 on/off

### 3.3 가드레일
- 표본 < 20건이면 **아무것도 바꾸지 않는다** (지금처럼 5건 상태에서 학습 금지)
- 학습 결과는 `meta`에 기록: 시각, 바뀐 값, 근거 표본 수, 검증 성적
- **모의매매에서만 자동 적용**. 실거래 파라미터는 자동 변경 금지(사람 확인)
- 검증 성적이 기존보다 나쁘면 자동 폐기 (되돌리기)

## 4. 실시간 신호

### 4.1 경로
```
토스 웹소켓(체결) → 수집기 _on_trade (즉시)
   ├─ 버스트/전조 판정 (최근 60초 거래대금·회전율)
   ├─ events 테이블에 즉시 기록 (ts, symbol, kind, text, value)
   ├─ 텔레그램 푸시 (dedupe: 같은 종목·종류 10분)
   └─ 매매 엔진: events 를 1초 간격으로 확인 → 조건 충족 시 즉시 주문
```

### 4.2 지연 목표
| 구간 | 목표 |
|---|---|
| 체결 → 신호 판정 | ≤ 1초 |
| 신호 → 주문 전송 | ≤ 2초 |
| 신호 → 텔레그램 도착 | ≤ 2초 |

### 4.3 구현 방식
- 수집기: 기존 `TossStream(channels=("trade",), on_trade=...)` 재사용. 신호 판정은 이벤트 콜백 안에서 (현재는 별도 스레드 `_rt_worker`).
- 매매 엔진: 지금 15초 주기 스캔 → **`events` 신규 행 감지 시 즉시 스캔** 추가 (1초 폴링, 인덱스 `ix_events_ts` 사용).
- 실패 시: 웹소켓이 끊기면 기존 REST 1분 폴링으로 자동 폴백 (이미 있음).

## 5. 안전장치

- 학습이 만든 규칙도 기존 리스크(1% 손실, 동시보유 8, 08:50 청산)를 **우회하지 못한다**
- 놓친 러너 데이터에는 **미래 정보가 섞이지 않게** as-of 규칙 적용 (그 시각까지 알려진 값만)
- 백필 데이터와 실시간 데이터는 `source` 컬럼으로 구분 (재현성)

## 6. 검증

| 항목 | 방법 |
|---|---|
| 데이터셋 정확성 | 10/28 실제 +30% 종목列表를 관리자 화면/`runner_events`로 대조 |
| 미스 분류 | 임의의 놓친 러너 5건을 골라 분류가 말이 되는지 수동 확인 |
| 실시간 지연 | `events.ts` → `orders.ts` 차이를 20건 측정해 중앙값 ≤ 3초 확인 |
| 학습 안전성 | 표본 19건일 때 아무것도 안 바뀌는지 테스트 |

## 7. 열린 결정

- 학습 모델: 로지스틱 회귀 vs 결정트리(깊이 3) vs 규칙 탐색 — **해석 가능성 우선으로 규칙 탐색 + 회귀 점수** 제안
- 과거 공매도·대차 데이터는 확보 불가 → 학습 초기에는 가격·거래량·유통주식·공시 특징만 사용
- 분봉 백필 범위: 전체가 아니라 **러너 이벤트가 난 종목·날짜만** (비용 통제)

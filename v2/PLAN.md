# pennybot2 — 처음부터 다시 만들기 계획

> 먼저 읽을 것: [`LESSONS.md`](LESSONS.md) — 기존 버전에서 가져온 주의사항과 나쁜 점·고친 방법.

기존 `pennybot/`(약 3만 줄)은 **그대로 두고**, `v2/` 폴더 안에 새로 만든다. 마음에 들면 갈아타고, 아니면 기존 것을 계속 쓴다.
변경 기록은 `v2/CHANGELOG.md` (루트의 `CHANGELOG.md` 는 기존 버전 것).
`v2/` 안에서 `python -m pytest -q` 로 테스트, 상태 파일은 `v2/state/`.

## 원칙
- 시세는 LS증권 OpenAPI 하나만 (토스 코드 없음). 매매 일꾼은 아직 없음 — 만들 때 모의가 기본, 실거래는 `mode: live` + `PENNYBOT_LIVE_CONFIRM=YES` 둘 다 있어야 하는 안전장치를 함께 둔다.
- 줄 수가 아니라 쓸모 기준: 목표에 쓰이는 것만 두고, 같은 일을 하는 건 하나로 합치고, 안 쓰이는 건 지운다 (제대로 된 코드면 길어도 됨).
- 파일 입출력은 항상 `encoding="utf-8"`.

## 구조 (2026-11-25 재확정: 허브 + 따로 도는 일꾼)
데이터는 허브 한 곳으로 모으고, 수집·감지·알림은 각각 별도 프로세스(일꾼). 일꾼은 허브하고만 대화(JSON 줄, 로컬 TCP).
허브는 메모리 전달 우선, 저장은 1초 배치. 한 일꾼이 죽거나 느려도 나머지는 계속. 지연 목표: 로컬 전달 수 ms.

## 3단계 실제 연결 확인 체크리스트 (LS 키 있는 PC 에서)
1. `.env` 에 `LS_APP_KEY`, `LS_APP_SECRET` → `python -m pennybot2 hub` 와 `python -m pennybot2 ls` 를 각각 켠다
2. 로그에 `LS 종목 마스터: N종목` → `구독 종목 N개` → 1분 뒤 `수신 {'frames': …, 'ticks': …}` 가 늘어나는지
3. 확인할 것: 마스터 행에 `keysymbol` 이 실제로 들어 있는지(없으면 구독 0개), `clos`·`suspend` 값 형식, 틱 시각(`trdtm`)이 미동부 시각인지
4. 응답 코드 `10003`(전송 한도)·토큰 오류가 반복되면 `SUBS_PER_SEC` 를 낮춘다

## 4단계 실제 확인 체크리스트 (인터넷 되는 PC 에서)
1. `python -m pennybot2 hub` 와 `python -m pennybot2 daily` 를 켠다 (LS 키 없으면 DB 에 일봉이 있는 종목만 대상 — 처음엔 비어 있으니 LS 키 필요)
2. 로그: `일봉 동기화 시작: 목표 …` → `일봉 동기화 결과: {requested, rows, failed}` → `후보 N개 (기준 …)`. failed 가 많으면 야후 429(너무 빠름) → `sync(..., workers=2, pause=0.5)`
3. 후보 개수가 기존 `pennybot` 의 5점↑ 목록과 비슷한지 비교 (점수 계산은 기존 것과 같은 결과임을 테스트로 확인함 — 틀어지면 일봉 데이터 차이)

## 5-1 기존 알림 재채점 체크리스트 (기존 봇 데이터가 있는 PC 에서)
1. `v2/` 안에서: `python -m pennybot2 grade ..\state\market.db` (기존 DB 는 읽기 전용으로 열림). 옵션: `--kind=burst` 종류 하나만, `--cost=1.0` 한쪽 비용 %, `--controls=3000` 대조군 수
2. 읽는 법: 등급(★★·★·등급 없음·A/B/C)별로 '+10%먼저'가 대조군보다 높고 **세 기간 모두** 유지될 때만 '효과 있음'. '표본 부족'·'불확실'은 결론 아님
3. 확인할 것: ★★ 와 ⚠ 만 구분되고 ★ 과 '등급 없음'이 겹치는지(기존 기록상 그랬음), 빠른 알림이 대조군보다 정말 나은지, 알림 종류별 순위
4. 결과 표를 그대로 `v2/LESSONS.md` 에 붙여 두면 다음 세션이 이어받을 수 있음

## 6단계 윈도우에서 확인할 것
1. `setup.bat` → `.env` 에 LS 키 입력 → `start.bat`. 창 하나에서 허브·일꾼이 따로 켜지고, 다른 창에서 `pennybot.bat status` 가 일꾼 5개를 ✅ 로 보여 주는지
2. `start.bat` 을 한 번 더 켜면 '이미 실행 중' 으로 끝나는지 (윈도우 PID 확인 `core/lock.py` 의 ctypes 부분 검증)
3. 일꾼 하나를 작업 관리자에서 끝내면 몇 초 뒤 감독자가 다시 켜고, 30초 넘게 보고가 없으면 텔레그램/웹훅으로 '응답 없음' 이 오는지
4. 장중에 LS 연결이 끊기면 3~5분 뒤 '시세 끊김' 알림, 17~20시(ET)·주말에는 안 오는지

## 후보 모델 학습 체크리스트 (일봉 이력이 있는 PC 에서)
1. `v2/` 안에서 `python -m pennybot2 train ..\state\market.db` (몇 분). 시험 구간 급등이 100건 넘어야 판단함
2. 읽는 법: ① 확률 손실이 평균 비율보다 낮나 ② 하루 상위 56·200 포착률이 기존 규칙 점수보다 높나 ③ 교정 표에서 예측 확률과 실제 급등률이 비슷한가 ④ '학습된 요인'의 부호가 상식·조사 내용(LESSONS G절)과 맞나 (새 기준 brk20·gap20·red3·volcomp 의 부호 포함; 20·60일 급등 횟수 기준은 쓰지 않음)
3. 채택되면 `state/model.json` 이 생기고 일봉 일꾼이 이 모델로 후보 200개를 뽑으며 알림에 '급등 확률 약 N%' 가 붙음. 채택 안 되면 이유가 출력되고 기존 규칙 점수가 계속 쓰임
4. 결과를 `LESSONS.md` I절에 붙이고, 정기적으로(예: 매주) 다시 학습·시험

## 조기 감지 채점 체크리스트 (1분봉 이력이 있는 PC 에서)
1. `v2/` 안에서 `python -m pennybot2 backtest-ignite ..\state\market.db --out=state\bt.db` (종목별로 돌므로 몇 분)
2. `python -m pennybot2 grade ..\state\market.db --alerts-db=state\bt.db` → '알림 종류별' 표에서 `ignite:fast/early/strict`, `stir`, `surge`(늦은 감지)를 대조군과 비교. '일관됨'이 아니면 채택하지 않음
3. 볼 것: ① 조기 감지가 늦은 감지보다 +10%먼저 비율이 높은가(손실 −5%먼저는 낮은가) ② 신호 수(하루 몇 건인가 — 너무 많으면 알림 피로) ③ 세션별(프리·정규·데이) 차이 ④ `stir`(거래만 먼저)가 이후 상승으로 이어지나 — 이어지면 가격 상승 전에 알릴 수 있음
4. 실시간으로 며칠 돌린 뒤 `grade state/market.db`(v2 의 signals 표)로 다시 채점 — 틱 단위 신호(`early` 포함)는 여기서만 제대로 평가됨
5. 결과를 `LESSONS.md` J절에 붙이고, 채택한 규칙만 `notify=True` 로 바꾼다(`Variant`)

## 반응 전 징후 연구 체크리스트 (1분봉 이력이 있는 PC 에서)
1. `v2/` 안에서 `python -m pennybot2 precursor ..\state\market.db --max-symbols=300` (종목 300개 기준 분 단위 계산 두 번 훑음 — 수 분~수십 분). 기간을 줄이려면 `--since=2026-10-15`
2. **연구 A 표**: 행=특징, 열=급등 시작 N분 전. ✔ 가 1분 전부터 쭉 이어지는 특징이 '반응 전 징후'. 이어지는 가장 이른 시점이 '몇 분 먼저 알 수 있는가'
3. **연구 B 표**: 기존 방식과 같은 알림 수(×1)에서 ① '급등이 이어짐' 비율을 유지하나 ② 반응 전 포착률이 얼마나 높나 ③ 평균 몇 분 먼저인가 ④ 알림을 늘리면(×2, ×4) 정밀도가 무너지는 지점. 시험 사건 50건 미만이면 판단 불가
4. 민감도: `--run=0.15`·`--run=0.30`, `--horizon=20`, `--K=5` 로 바꿔도 같은 징후가 남는지. 남지 않으면 정의에 의존한 결과
5. 결과를 `LESSONS.md` K절에 붙이고, 징후가 일관되면 같은 특징을 실시간(허브 분봉)으로 계산하는 `ignite` 규칙으로 승격
